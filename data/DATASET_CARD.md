## MMQA schema (discovered, not assumed)

The original spec assumed MMQA would ship as a small annotation file referencing separate
Spider `.sqlite` files. The actual format (discovered via
`src/mmqa_schema_probe.py`, see full findings in the `src/mmqa_ingest.py` docstring)
is different in ways that change Stage A/E for MMQA specifically:

- Each instance embeds **full row content** for its 2–3 tables directly (not a
  `db_id` reference) — this is why the files are hundreds of MB. Stage A for MMQA is
  "materialize a temp SQLite DB per instance from embedded rows," not "point at an
  existing `.sqlite` file."
- No `db_id` field at all. Instances are mapped back to their Spider `db_id` by matching
  table names and columns (3,276 of 3,313 match exactly one DB); the rest are grouped by a
  derived `schema_signature` for the database-level split.
- `primary_keys` / `foreign_keys` are flat column-name lists, not positionally aligned
  to `table_names` and not reliably one-per-table or one-per-edge (composite keys
  contribute multiple entries). Must be resolved by name-matching against each table's
  columns, not by position.
- Column-name formatting is **inconsistent between the two files**
  (`Synthesized_three_table.json` uses source casing with underscores, e.g.
  `"head_ID"`; `Synthesized_two_table.json` uses lowercased words with spaces, e.g.
  `"head id"`). Any FK/PK name-matching must normalize both sides first.
- `answer` is a single joined string, not a list, and unsafe to parse (comma-split
  breaks if a value contains a comma). `gold_answer` will instead come from executing
  `SQL` against the materialized per-instance SQLite DB, exactly as Stage E already
  does for Spider and BIRD — `answer` is kept only as an audit cross-check field.

Full details and the exact record shape are documented at the top of
`src/mmqa_ingest.py`, which phase P1 implements against.

**MMQA data quality (see `DESIGN.md` §11):**
- MMQA's shipped answers vs executing its own gold SQL (3,114 questions whose SQL runs; a
  question counts as agreeing when every SQL result value appears in the shipped text):
  65% agree (differences are formatting only: sentences, 667 pandas-dict answers, joined or

  15% differ completely, 3% the SQL returns nothing. The original Spider DBs agree with our
  materialised tables on 382/386 sampled questions, so the mismatch is annotation noise in
  MMQA. Gold answers here come from SQL execution; the shipped text is kept as
  `reference_answer`.

## Regeneration

Built data: `notebooks/build_data.py` on molab runs
`python -m mhtable.data.build --family spider_mmqa --push` (and `--family bird`).

Raw sources are mirrored into the private HF dataset `mhtable-raw` (see `DESIGN.md` §4) by
`notebooks/source_data.py` on molab, which runs:

```bash
pip install -e ".[dev]"
python -m mhtable.data.source --sources spider mmqa bird
```

Expected checksums live in `src/mhtable/data/source.py` (`SOURCES`); the repo's
`CHECKSUMS.sha256` records what was actually mirrored. A checksum mismatch stops the run — that
is the trigger to investigate (and, if MMQA disappears upstream, to fall back to held-out
Spider/BIRD databases only).
